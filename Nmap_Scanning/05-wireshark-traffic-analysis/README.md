# Lab 05 - Network Traffic Analysis with Wireshark

Academic lab (Ethical Hacking Lab, Sem III) performed on Kali Linux in an
authorized, self-owned virtual environment.

**Topics:** `wireshark` · `kali-linux` · `network-analysis` · `cybersecurity` · `ethical-hacking`

## About
This lab covers capturing and analyzing live network traffic with **Wireshark** on
**Kali Linux**. I applied display filters (HTTP, DNS, TCP, UDP, ICMP, ARP), inspected
packet headers, and assessed unusual traffic patterns in an authorized virtual lab.
It builds foundational **network analysis** skills used in **cybersecurity** and
**ethical hacking**.

## Objective
Capture live network traffic, inspect common protocols with display filters,
and assess whether any observed traffic is unusual or suspicious.

## Environment
| Item | Detail |
|------|--------|
| Analysis host | Kali Linux VM (kernel 6.18, VirtualBox, NAT network `10.0.2.15`) |
| Tool | Wireshark 4.6.6 |
| Capture interface | `eth0` |
| Capture size | 1,827 packets |
| Traffic generated | `ping` (ICMP), DNS lookups, Firefox browsing (HTTP, TLS 1.3) |

## Methodology
1. Installed Wireshark and verified the version (`wireshark --version`).
2. Started a live capture on `eth0`.
3. Generated traffic: `ping google.com`, `ping example.com`, and web browsing.
4. Stopped the capture and saved it.
5. Applied display filters: `http`, `dns`, `tcp`, `udp`, `icmp`, `arp`.
6. Inspected Ethernet, IPv4, and TCP/UDP headers of selected packets.
7. Reviewed the traffic for anomalies and recorded findings with evidence.

## Findings

No confirmed malicious activity was found. This is expected: all traffic was
generated by me on a lab VM. The items below are the patterns that deserved a
closer look, and how I assessed each one.

| # | Finding | Evidence | Assessment | Recommended response |
|---|---------|----------|------------|----------------------|
| 1 | **TCP RST sent by the client right after a SYN-ACK.** `10.0.2.15:54080` reset its connection to `199.232.105.91:443` (packets 66-67) while a parallel connection on port 54078 completed TLS normally. | [09](screenshots/09-tls-and-tcp-rst.png) | Low risk. Consistent with the browser abandoning an extra connection. Repeated resets across many hosts or ports would be a scan indicator instead. | Filter `tcp.flags.reset == 1` and check *Statistics > Conversations* for volume; establish a baseline before alerting. |
| 2 | **Cleartext HTTP request** (`GET /success.txt?ipv4`) answered with `200 OK (text/plain)`. | [11](screenshots/11-filter-http.png) | Benign. Looks like a browser connectivity check. It shows that unencrypted HTTP exposes full request details to anyone on the path. | Prefer HTTPS; in a managed network, review any cleartext HTTP that carries credentials or user data. |
| 3 | **DNS "No such name" (NXDOMAIN) responses** for the single-label name `Admin` (A and AAAA) and for reverse lookups of pinged IPs. | [12](screenshots/12-filter-dns.png), [07](screenshots/07-capture-dns-icmp-arp-example.png) | Likely the VM resolving its own hostname plus automatic reverse lookups from `ping`. Benign here. A high rate of NXDOMAIN to many random-looking names would point to malware or misconfiguration. | Monitor NXDOMAIN rate per host; investigate bursts of unusual names. |
| 4 | **All ping replies show TTL 255**, including from external hosts. | [03](screenshots/03-ping-google.png), [06](screenshots/06-ping-example-com.png) | Likely an artifact of the VirtualBox NAT answering ICMP, not the remote host. A reminder that lab topology affects what you observe. | Note the environment when interpreting TTL-based conclusions. |
| 5 | **TLS 1.3 application data** to external hosts. | [09](screenshots/09-tls-and-tcp-rst.png) | Contents cannot be read without session keys. Only metadata (IPs, ports, SNI, sizes) is analyzable. | Use endpoint or proxy logging where payload visibility is needed. |

## Limitations and next steps
- The capture was benign by design, so it does not demonstrate detection of real attacks.
- UDP made up 62.5% of the capture. I did not break this down further; the next step is to filter `quic` to confirm it is browser HTTP/3 traffic.
- Planned extension: scan the VM from another lab host with Nmap and capture it, to examine real SYN/RST patterns and failed connection attempts using
  `tcp.flags.syn==1 && tcp.flags.ack==0`.

## What I learned
- How packets are layered (Ethernet, IP, TCP/UDP, application) and how to read each header.
- Display filters are the fastest way to separate signal from noise in a large capture.
- "Suspicious" depends on context: unusual traffic needs a baseline and verification, not assumptions.
- Encrypted traffic limits payload inspection to metadata.
